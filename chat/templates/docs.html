01Request path

Browser→ HTTP :80 → Nginx (location /viikko5/)→ 127.0.0.1:8005 → Gunicorn + Flask (user viikko5)
Flask→ 127.0.0.1:11434 →Ollama ({{ model }})   |   Flask→ local socket →MariaDB (viikko5chat)
  • Nginx strips the /viikko5 prefix (proxy_pass http://127.0.0.1:8005/;) and sends X-Forwarded-Prefix: /viikko5. Flask uses ProxyFix, so url_for() creates links such as /viikko5/static/style.css and /viikko5/api/chat.
  • Every browser gets a random session ID in an HttpOnly cookie. Messages are saved in MariaDB with that ID, and the page loads the conversation from the database. A new browser session or private window has no cookie, so it starts empty.
  • Only Nginx is reachable from the internet. Gunicorn and Ollama listen on 127.0.0.1 only (see the ss -ltnp output in section 09).

02CI/CD pipeline

Workflow file: .github/workflows/ci-cd.yml. It runs on every push and every pull request.

JobWhenWhat it does
testevery push and PR Installs Python 3.14 (same as Ubuntu 26.04), runs the linter ruff check . and the tests pytest. The tests replace the language model and the database with fakes, so they need neither.
deploypush to main only, needs: test Runs only if the test job passed. Copies the code with rsync over SSH as user deploy and runs sudo /usr/local/sbin/viikko5-deploy <github.sha>. Then checks the public health endpoint.

What the deployment script does (deploy/deploy.sh)

  1. Copies the code to /opt/viikko5/app (owner root, group viikko5, read-only for the app) and writes github.sha to REVISION.
  2. Installs the dependencies into the virtualenv /opt/viikko5/venv.
  3. Applies the database schema (CREATE ... IF NOT EXISTS, safe to run every time).
  4. Installs the systemd unit from the repository and runs daemon-reload.
  5. Installs the Nginx snippet, runs nginx -t and reloads Nginx only if the test passes. If the test fails, the old snippet is restored and the deployment stops.
  6. Restarts only viikko5.service. Other services are not touched.
  7. Polls http://127.0.0.1/viikko5/health until it returns the new SHA. If it does not, the script exits with an error and the workflow fails.

How a deployment is verified

The server-side script checks the health endpoint through Nginx, and the last workflow step checks it again from the internet: curl http://SERVER/viikko5/health must return "commit": "<github.sha>", otherwise the run is red.

  • Checked the ports in use first (ss -ltnp, systemctl list-units): Nginx :80, Week 2 Gunicorn 127.0.0.1:8000, MariaDB :3306, SSH :22. Chose the free port 127.0.0.1:8005 for Week 5.

06Is the chat database replicated to server B?

No. In Week 4 the master on server A was configured with binlog_do_db = viikko2 and the replica on B with replicate_do_db = viikko2. The new database viikko5chat is not written to the binary log, so it stays on A only. This is on purpose: B is a read-only replica for the Week 2 counter, the chat cannot write there, and chat messages can contain personal text that does not need a second copy. The chat runs on server A, as the assignment requires.

07How GitHub Actions reaches the server

GitHub's runners connect from changing IP addresses, so the cPouta security group allows SSH (TCP 22) from 0.0.0.0/0.

Security implications and what limits them

  • Anyone can try to connect to port 22, so password login is disabled and only keys work.
  • The GitHub Actions key is a separate key pair. It only logs in as deploy, it is restricted and the private key exists only in GitHub secrets.
  • known_hosts is a secret too, so the workflow refuses to connect if the server's host key changes (no man-in-the-middle).
  • The deploy user can run only the deployment script with sudo. That script installs a systemd unit, so the key is still powerful: if it leaks, it must be removed from authorized_keys and replaced at once.
  • Deployments run only from main after the tests pass. Pull requests from forks never get the secrets.
